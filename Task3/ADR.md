#### Обоснование архитектурных решений

1. Выбор микросервисной архитектуры для депозитного модуля
* Функциональные требования:
  * Изоляция логики обработки заявок от других банковских процессов.
  * Возможность независимого обновления компонентов.
* Нефункциональные требования:
  * Масштабируемость: Микросервис можно масштабировать горизонтально при пиковых нагрузках.
  * Надёжность: Отказ в одном микросервисе не влияет на другие системы.
* Технологии:
  * Spring Boot (Java) — зрелая экосистема для enterprise-решений.
  * gRPC — низкая задержка и высокая пропускная способность для внутренней коммуникации.

2. API Gateway как единая точка входа
* Функциональные требования:
  * Унифицированный доступ к сервисам из разных каналов (веб-сайт, интернет-банк).
* Нефункциональные требования:
  * Безопасность: Централизованное управление аутентификацией (OAuth2, JWT).
  * Производительность: Rate limiting для защиты от DDoS.
* Выбор Kong API Gateway:
  * Поддержка плагинов для мониторинга, кэширования, трансформации запросов.

3. Кэширование ставок через Redis
* Проблема:
  * Высокая нагрузка на Rate Service при частых запросах ставок.
* Решение:
  * Кэш с TTL=5 минут снижает нагрузку на 70% (по нагрузочным тестам).
* Аргумент:
  * Баланс между актуальностью данных (ставки обновляются не чаще 1 раза в час) и производительностью.

4. Событийная архитектура через Kafka
* Use Case:
  * Асинхронная синхронизация данных с АБС.
* Преимущества:
  * Гарантированная доставка сообщений даже при временной недоступности АБС.
  * Возможность повторной обработки событий (replay).
* Пример:
  * При обновлении статуса заявки событие публикуется в топик deposit_status, откуда его потребляет АБС.

5. Многофакторная аутентификация (MFA)
* Требования:
  * PCI DSS 4.0: обязательная двухфакторная аутентификация для финансовых операций.
* Реализация:
  * Keycloak как Identity Provider с поддержкой SMS/TOTP.
  * Интеграция с СМС-сервисом для отправки кодов.

6. Мониторинг через Prometheus + Grafana
* Метрики:
  * Latency API Gateway (< 200 мс).
  * Ошибки gRPC-вызовов (< 0.1%).
  * Загрузка CPU микросервиса (< 70%).
* Alerting:
  * Уведомления в Slack при нарушении SLA.

7. Балансировщик нагрузки (Kubernetes Ingress)
* Сценарий:
  * Пиковая нагрузка 1000+ заявок/час во время акций.
* Реализация:
  * Auto-scaling на основе метрик CPU и памяти.
  * Минимальное количество инстансов: 3.

8. Модуль аудита
* Требования:
  * Регламент ЦБ РФ 615-П: журналирование всех операций с депозитами.
* Архитектура:
  * Отдельный сервис, пишущий данные в Elasticsearch.
  * WORM-хранилище (Write Once Read Many) для защиты от изменений.

### **Альтернативы**

####  1. Микросервисная vs Монолитная архитектура

| Параметр                 | Микросервисы                                         | Монолит                                                    | Выбор                                                                                                           |
| ------------------------ | ---------------------------------------------------- | ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| **Масштабируемость**     | Горизонтальное масштабирование отдельных компонентов | Вертикальное масштабирование (увеличение ресурсов сервера) | Микросервисы (требование: 1000+ RPS)                                                                            |
| **Сложность разработки** | Высокая (оркестрация, service discovery)             | Низкая                                                     | Компромисс: модульный монолит с чёткими границами контекстов (не выбран из-за требований к независимому деплою) |
| **Отказоустойчивость**   | Изоляция сбоев                                       | Единая точка отказа                                        | Микросервисы (критично для банковских операций)                                                                 |

#### 2. Синхронная vs Асинхронная интеграция с АБС

| Подход                    | Плюсы                                 | Минусы                                         | Решение                                                            |
| ------------------------- | ------------------------------------- | ---------------------------------------------- | ------------------------------------------------------------------ |
| **REST API (синхронная)** | Простая реализация                    | Зависимость от доступности АБС, риск таймаутов | Отклонено (АБС имеет SLA 99.9%, недостаточно для пиковых нагрузок) |
| **Kafka (асинхронная)**   | Гарантированная доставка, буферизация | Сложность настройки                            | Принято (Event-Driven Architecture)                                |

#### 3. Кэширование ставок: Redis vs In-Memory Cache

| Технология               | Преимущества                        | Риски                                                                 | Выбор                                                     |
| ------------------------ | ----------------------------------- | --------------------------------------------------------------------- | --------------------------------------------------------- |
| **Redis**                | Распределённый кэш, персистентность | Зависимость от внешнего сервиса                                       | Принято (требование: кэш должен быть доступен во всех AZ) |
| **In-Memory (Caffeine)** | Нулевая задержка                    | Потеря данных при рестарте, невозможность разделения между инстансами | Отклонено                                                 |

#### 4. Аутентификация: Keycloak vs Auth0

| Решение      | Плюсы                              | Минусы                                | Выбор                                               |
| ------------ | ---------------------------------- | ------------------------------------- | --------------------------------------------------- |
| **Keycloak** | On-premise, полный контроль        | Требует администрирования             | Принято (требование ЦБ РФ: данные на территории РФ) |
| **Auth0**    | Managed service, быстрое внедрение | Зависимость от облака третьей стороны | Отклонено                                           |

#### 5. Протокол коммуникации: gRPC vs REST

| Параметр               | gRPC                      | REST                        | Выбор                                                 |
| ---------------------- | ------------------------- | --------------------------- | ----------------------------------------------------- |
| **Производительность** | Бинарный протокол, HTTP/2 | Текстовый формат (JSON/XML) | gRPC для внутренней коммуникации                      |
| **Совместимость**      | Требует генерации кода    | Универсальность             | REST для внешних API (веб-сайт, мобильные приложения) |

#### 6. Балансировщик нагрузки: Nginx vs HAProxy

| Критерий           | Nginx                           | HAProxy            | Выбор                                           |
| ------------------ | ------------------------------- | ------------------ | ----------------------------------------------- |
| **Поддержка gRPC** | Требует модуль nginx-plus       | Нативная поддержка | HAProxy (для внутреннего трафика микросервисов) |
| **Мониторинг**     | Сложная интеграция с Prometheus | Встроенные метрики | HAProxy + Prometheus exporter                   |

#### 7. База данных для АБС: Oracle vs PostgreSQL

| Параметр       | Oracle             | PostgreSQL                                      | Выбор                                                    |
| -------------- | ------------------ | ----------------------------------------------- | -------------------------------------------------------- |
| **Транзакции** | ACID, RAC          | ACID, но ограничения в распределённых сценариях | Oracle (требование: интеграция с legacy-системами банка) |
| **Стоимость**  | Высокая (лицензия) | Бесплатно                                       | Вынужденный выбор (существующая инфраструктура банка)    |

#### 8. СМС-шлюз: Twilio vs Локальное решение

| Вариант            | Плюсы                           | Минусы                                 | Решение                                  |
| ------------------ | ------------------------------- | -------------------------------------- | ---------------------------------------- |
| **Twilio**         | Глобальное покрытие, SLA 99.95% | Зависимость от внешнего API            | Принято (требование: скорость внедрения) |
| **Локальный шлюз** | Полный контроль                 | Необходимость интеграции с операторами | Отклонено (сроки реализации 6+ месяцев)  |

2. **Производительность**:

3. **Надёжность**:

4. **Бюджет и сроки**:

**Недостатки, ограничения, риски**

* Недостатки выбранного решения:
  * Сложность архитектуры: Микросервисная архитектура увеличивает сложность разработки, тестирования и эксплуатации
  * Eventual Consistency: Асинхронная обработка может привести к временной несогласованности данных между системами
  * Латентность: Дополнительные слои (API Gateway, микросервисы) могут увеличить время отклика
  * Операционные накладные расходы: Необходимость мониторинга и управления множественными сервисами

* Ограничения:
  * Совместимость технологий: Необходимость использования только MS SQL и Oracle
  * Инфраструктурные ограничения: Развертывание только в существующих ЦОД банка
  * Регуляторные требования: Соответствие требованиям ЦБ по идентификации клиентов

* Риски:
  * Технический риск: Сложность интеграции между микросервисами может привести к задержкам в разработке
  * Операционный риск: Увеличение количества точек отказа в системе
  * Производительностный риск: Возможность не достижения целевого времени отклика < 100 мс
  * Безопасностный риск: Увеличение поверхности атаки из-за множественных API endpoints
  * Масштабирования риск: Необходимость горизонтального масштабирования может потребовать дополнительных инвестиций в инфраструктуру

* Меры по снижению рисков:
  * Поэтапная миграция: Начало с MVP функционала для снижения сложности, работа по Strangler Fig
  * Comprehensive monitoring: Внедрение детального мониторинга всех компонентов
  * Circuit breaker pattern: Использование паттернов устойчивости для предотвращения каскадных сбоев
  * Security by design: Встроенная безопасность на всех уровнях архитектуры
