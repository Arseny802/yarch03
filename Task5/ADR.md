#### Логика принятия архитектурных решений

##### 1. **Выбор gRPC вместо REST (ASR-01)**
- **Обоснование**: 
  - **Производительность (NFR-01, NFR-02)**: gRPC использует бинарный протокол (Protobuf), что снижает нагрузку на сеть и ускоряет обработку запросов.
  - **Строгая типизация**: Автоматическая генерация клиентских библиотек уменьшает ошибки интеграции.
  - **Поддержка потоков**: Критично для ML-скоринга (UC-102), где требуется передача больших объёмов данных.
- **Компромисс**: Усложнение дебагга по сравнению с REST.

##### 2. **Изоляция кредитного модуля в VPC (ASR-02)**
- **Обоснование**:
  - **Безопасность (NFR-04)**: Отдельный сетевой сегмент защищает PII-данные от перекрёстного доступа.
  - **Соответствие PCI DSS**: Требование регуляторов для обработки финансовой информации.
  - **Управление трафиком**: Возможность тонкой настройки firewall правил для Kafka и БД.
- **Компромисс**: Увеличение сложности управления инфраструктурой.

##### 3. **Шина событий на Kafka (ASR-07)**
- **Обоснование**:
  - **Масштабируемость (NFR-01)**: Горизонтальное масштабирование потребителей топиков.
  - **Надёжность (NFR-03)**: Репликация данных между брокерами гарантирует сохранность событий.
  - **Интеграция с legacy (UC-105)**: Kafka Connect позволяет синхронизироваться с АБС без изменения её кода.
- **Пример**: Для UC-101 асинхронная обработка заявок через топик `credit.applications` снижает нагрузку на API.

##### 4. **Универсальный адаптер для БКИ (NFR-07)**
- **Обоснование**:
  - **Гибкость интеграции**: Поддержка SOAP/XML (НБКИ) и REST/JSON (Equifax) через единый интерфейс.
  - **Митигация рисков**: Заглушки с mock-данными позволяют тестировать систему до готовности внешних API.
  - **Кэширование**: Redis хранит часто запрашиваемые кредитные истории, снижая нагрузку на БКИ.
- **Компромисс**: Необходимость поддержки устаревших протоколов (напр., SOAP 1.1).

##### 5. **ML Engine на Python (UC-102)**
- **Обоснование**:
  - **Скорость разработки**: Библиотеки (scikit-learn, TensorFlow) ускоряют внедрение моделей.
  - **A/B-тестирование (ASR-05)**: Возможность параллельного запуска моделей для оценки эффективности.
  - **Интерпретируемость**: SHAP-анализ для объяснения скоринга (требование ЦБ РФ).
- **Ограничение**: Необходимость контейнеризации (Docker) для интеграции с Java-сервисами.

##### 6. **Circuit Breaker + Istio (ASR-04)**
- **Обоснование**:
  - **Отказоустойчивость (NFR-03)**: Автоматическое отключение нерабочих нод БКИ.
  - **Балансировка нагрузки**: Распределение запросов между экземплярами Scoring Engine.
  - **Метрики**: Istio предоставляет Prometheus-метрики для анализа SLA.
- **Пример**: При падении БКИ система переключается на кэш, сохраняя работоспособность UC-102.

##### 7. **FPE-шифрование (NFR-04)**
- **Обоснование**:
  - **Сохранение формата**: Номер паспорта "40 12 345678" шифруется в "59 83 294751", что не ломает интеграции.
  - **Совместимость с legacy**: АБС обрабатывает данные без модификаций.
  - **Соответствие 152-ФЗ**: Шифрование на уровне приложения, а не СУБД.
- **Инструменты**: Использование Vault для управления ключами.

#### Баланс между требованиями

1. **Производительность vs Безопасность**:
   - gRPC ускоряет коммуникацию, но требует mTLS для защиты каналов.
   - FPE замедляет запросы на 15-20 мс, что компенсируется кэшированием в Redis.

2. **Гибкость vs Стандартизация**:
   - Универсальный адаптер для БКИ поддерживает разные протоколы, но увеличивает сложность.
   - OpenAPI-спецификации (ASR-06) стандартизируют внешние API, упрощая интеграцию.

3. **Масштабируемость vs Стоимость**:
   - Kafka позволяет масштабироваться, но требует выделенного кластера.
   - Автоматическое масштабирование Pods в Kubernetes снижает затраты при низкой нагрузке.

4. **Скорость вывода vs Регуляторные требования**:
   - TTL=5 лет в PostgreSQL (ASR-03) автоматизирует выполнение 152-ФЗ.
   - Audit trail (NFR-05) записывается в отдельный микросервис, чтобы не замедлять основной процесс.

#### Критические зависимости

1. **Качество ML-моделей**:
   - Точность скоринга влияет на уровень одобрений и риски дефолтов.
   - Решение: Регулярное переобучение моделей на свежих данных.

2. **Скорость интеграции с БКИ**:
   - Задержки могут сорвать сроки релиза.
   - Решение: Параллельная разработка адаптеров и mock-сервисов.

3. **Производительность ЭЦП-платформы**:
   - Подписание 1000+ документов в час требует оптимизации.
   - Решение: Асинхронная обработка через Kafka с буферизацией.

##### Критические решения и компромиссы

1. **Микросервисы vs Монолит**
 - **Выбрано**: Микросервисы с изолированным Credit Service
 - **Причина**: Соответствие ASR-02 (изоляция VPC) и NFR-03 (99.95% uptime)
 - **Компромисс**: Увеличилась сложность оркестрации (требуется Kubernetes)

2. **gRPC vs REST**
 - **Выбрано**: gRPC с Protobuf
 - **Причина**: Обеспечение NFR-01 (1000 RPM) за счёт бинарного протокола
 - **Компромисс**: Необходимость внедрения gRPC Gateway для веб-клиентов

3. **Kafka vs RabbitMQ**
 - **Выбрано**: Apache Kafka
 - **Причина**: Поддержка ASR-08 (Near-Real-Time репликация) и обработка 10K+ событий/сек
 - **Компромисс**: Высокий порог входа для разработчиков

4. **FPE vs Традиционное шифрование**
 - **Выбрано**: Format-Preserving Encryption
 - **Причина**: Соответствие NFR-04 (без модификации legacy-систем)
 - **Компромисс**: Ограниченный выбор криптопровайдеров (используем Vault)

5. **Универсальный адаптер БКИ vs Прямые интеграции**
 - **Выбрано**: Адаптерный слой с плагинами
 - **Причина**: Выполнение NFR-07 (поддержка 3+ провайдеров)
 - **Компромисс**: Увеличение времени разработки на 20%

#### Технические ограничения

1. **Совместимость форматов**:
   - SOAP-адаптеры для БКИ требуют ручного сопровождения WSDL
   - Ограничение: Автогенерация кода только для REST API (OpenAPI)

2. **Производительность FPE**:
   - Шифрование 1 млн записей/час требует 8 vCPU
   - Ограничение: Нельзя использовать на edge-устройствах

3. **Репликация данных**:
   - Задержка 900 мс между DC нарушает ASR-08 (<1 сек)
   - Решение: Оптимизация через WAN-ускорители

4. **ML-модели**:
   - Точность моделей падает на long-tail данных
   - Ограничение: Необходимость еженедельного переобучения

#### Критические риски

#### Архитектурные компромиссы

1. **Скорость vs Надёжность**:
   - Выбрано: Асинхронная обработка через Kafka (скорость)
   - Жертвуем: Мгновенной консистентностью данных

2. **Гибкость vs Производительность**:
   - Выбрано: Универсальный адаптер БКИ (гибкость)
   - Жертвуем: 12-15% производительности на трансформацию форматов

3. **Безопасность vs Удобство**:
   - Выбрано: 2FA для всех операций (безопасность)
   - Жертвуем: Увеличением времени подписания на 20%

4. **Стоимость vs Масштабируемость**:
   - Выбрано: Автомасштабирование Pods (масштабируемость)
   - Жертвуем: Ростом расходов на облако на 30%
